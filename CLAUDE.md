# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

VST Work Tools — a PySide6 desktop app with three tools, each a tab in the main window: **ACS Log Parser** (downloads ACS/3-D Secure Access Control Server logs from Elastic, parses them into daily CSVs, builds DuckDB-powered Excel pivot reports), **3DS Log Parser** (same download → parse → report flow, mirrored for 3DS Server logs — a different Elastic log source with its own message vocabulary), and **Parser** (a standalone number-list formatting/dedup utility, unrelated to either log parser). Everything lives under `backend/`; there is no frontend/, server, or API — it's a single-machine desktop tool. Distributed as a PyInstaller onefile exe (`VST.exe`) with no Python install required on the target machine.

## Commands

All commands run from `backend/`.

```bash
pip install -r requirements.txt
cp .env.example .env                  # fill in ELASTIC_PASS (required) before running
python -m desktop                     # run the app in dev mode (uses backend/data/)
python -m unittest discover -s tests -p "test_*.py" -v   # run all tests
python -m unittest tests.test_auth_method_switch_ids -v  # run a single test module
build.bat                             # (or build.sh) installs deps + pyinstaller, builds dist/VST.exe via vst.spec
```

`pyrightconfig.json` at the repo root type-checks `backend/app` and `backend/desktop`.

Git hooks: run `setup-hooks.sh` (or `.bat`) once to point `core.hooksPath` at `.githooks`. The `pre-push` hook runs the same `unittest discover` command before every push — keep it green.

## Configuration (`.env`)

`app/common/config.py`'s `load_env_file()` reads `.env` (next to `VST.exe` when frozen, `backend/.env` in dev) at startup and sets any var **not already present** in the environment — existing env vars always win. See `.env.example` for the full list; `ELASTIC_PASS` is the only required one. `build.bat`/`build.sh` copy `backend/.env` to `dist/.env` after every build. Other notable vars: `ELASTIC_USER`/`ELASTIC_URL`/`ELASTIC_INDEX`/`ELASTIC_TIME_ZONE` (query shape, shared by both Elastic log sources), `ELASTIC_HOSTS`/`ELASTIC_APP_NAME` (ACS Log Parser's query filters, default hosts `acss201`/`acss202`), `ELASTIC_3DS_APP_NAME`/`ELASTIC_3DS_HOSTS` (3DS Log Parser's query filters, default hosts `3dss201`/`3dss202`), `ELASTIC_VERIFY_TLS`/`ELASTIC_CA_BUNDLE` (TLS, off by default — internal endpoint uses a self-signed cert), `ELASTIC_MAX_DROPPED`/`PARSER_MAX_DROPPED` (data-integrity thresholds, see below — shared by both parsers), `LOG_STORAGE_DIR`/`CSV_STORAGE_DIR`/`REPORT_OUTPUT_DIR` (ACS path overrides) / `THREEDS_LOG_STORAGE_DIR`/`THREEDS_CSV_STORAGE_DIR`/`THREEDS_REPORT_OUTPUT_DIR` (3DS path overrides), `REPORT_EMAIL_TO`/`REPORT_EMAIL_SUBJECT` (recipient(s)/subject for ACS report emails sent via Outlook COM automation — ACS only, the 3DS Report tab has no email option yet; `app/acs/services/report_mailer.py` is the single file with recipients/subject/default body-text/send logic for these emails).

## Architecture

### Three Python package trees: `app/common/`, `app/acs/`, `app/threeds/` (headless logic) and `desktop/` (PySide6 UI)

`app/common/` holds genuinely source-agnostic code shared by both log-parsing tools: `config.py` (env file loading), `paths.py` (`get_app_root`/`get_bundle_dir`/`ROOT_DIR`/`DB_DIR` — exe/script location + bundled `db/` dir resolution), `elastic_logs.py` (the generic Elastic-download engine), `parse_diagnostics.py` (`ParseDiagnostics`/`max_dropped_lines` — generic drop-tracking for any log parser), `device_detection.py` (`parse_browser_device` — user-agent → OS/model sniffing, used by both CSV writers), `duckdb_time_zone.py` (`register_time_zone_functions` — the `vst_st_louis_date` UDF, used by both report engines), `excel_pivot.py` (`add_native_pivot` — generic Excel COM pivot-table builder, parameterized by `row_fields`/`value_field`, no ACS/3DS-specific code), `report_utils.py` (date normalization, custom-SQL validation, cell formatting, `ReportResult` — generic report-param helpers). `app/acs/` and `app/threeds/` each have their own `paths.py` (storage directory getters) and `elastic_config.py` (an `ElasticSourceConfig` instance — which `app_name`/`hosts` env vars and defaults that source's Elastic queries use), and each has its own full `parsers/` + `services/` tree mirroring the other's structure (see below) — the two log formats are different enough (different JSON message types, different plain-text patterns) that the parsing/report-SQL logic itself is NOT shared, only the atomic pieces above are.

`desktop/` mirrors this: `desktop/widgets/common.py` and `desktop/theme.py` are genuinely shared (generic Card/button widgets, the app-wide stylesheet); each tool's tab, widgets, and QThread workers live under `desktop/tools/{acs,threeds,parser}/` — again mirrored structure, not shared code, since each tool's Report tab binds to its own SQL template and column names. `desktop/` never touches parsing/storage internals directly except through `app.*` functions — the UI is a thin driver over the backend logic and long-running work runs in QThread workers so the UI stays responsive.

- `desktop/tools/parser/parser_tab.py` (+ `parsing_tools.py`) — standalone number-list formatting/dedup utility (SQL-quoted or plain), unrelated to either log parser.
- `desktop/tools/acs/acs_tab.py` — the ACS Log Parser tab: **Import & Parse** downloads a date range from Elastic and parses it into daily CSV, **Report** picks a range and runs/exports the pivot report (including emailing it). Backed by `widgets/import_parse_panel.py`, `widgets/coverage_sidebar.py` (+ `desktop/tools/acs/coverage_utils.py` for per-day status/action derivation), `widgets/report_panel.py`, and `desktop/tools/acs/workers.py`.
- `desktop/tools/threeds/threeds_tab.py` — the 3DS Log Parser tab: same **Import & Parse** / **Report** shape as the ACS tab, plus a third **Raw Log** sub-tab (reads the raw downloaded text for a single selected day via `app/threeds/log_storage.py`'s `read_log_content`). Backed by `widgets/download_panel.py` (download + per-day **Parse**/**Re-parse** button), `widgets/coverage_sidebar.py`, `widgets/log_viewer.py`, `widgets/report_panel.py` (identical to the ACS one minus the email compose dialog/checkbox — not built for this source yet), `desktop/tools/threeds/coverage.py` (status model: `ready`/`partial`/`parsing`/`parsed`/`failed`, mirrors `coverage_utils.py`), `report_sql_utils.py`/`report_table_utils.py` (mirror the ACS ones — same string-matching logic works because the 3DS SQL template uses the same `areq.messagedatetime`/`areq.threedsservertransid` naming convention), and `desktop/tools/threeds/workers.py`.
- `desktop/__main__.py` loads `.env` and installs a crash hook that appends uncaught exceptions to `vst-error.log` next to the exe/`.env`, before importing `desktop.main_window` (import errors get logged too).

### Elastic download engine (`app/common/elastic_logs.py`) + per-source config (`app/acs/elastic_config.py`, `app/threeds/elastic_config.py`)

Logs are downloaded from Elastic via a SQL-over-HTTP proxy endpoint (`_sql?format=csv`), not uploaded manually. The engine is source-agnostic: every entry point (`build_query_body`, `download_day`) takes an explicit `ElasticSourceConfig` (`app_name_env`/`app_name_default`/`hosts_env`/`hosts_default` — `hosts_env=None` would mean the query has no `AND host IN (...)` clause at all, but neither current source uses that) — there is no hidden default, every call site passes its own config. `ACS_SOURCE` (`app/acs/elastic_config.py`): `ELASTIC_APP_NAME`/`ELASTIC_HOSTS`, default `solar-acs` + `acss201`/`acss202`. `THREEDS_SOURCE` (`app/threeds/elastic_config.py`): `ELASTIC_3DS_APP_NAME`/`ELASTIC_3DS_HOSTS`, default `solar-3ds-server` + `3dss201`/`3dss202`.

`download_day()` fetches a calendar day in 30-minute chunks (basic auth via `ELASTIC_USER`/`ELASTIC_PASS`), recursively bisecting a chunk down to 1-minute windows on a retryable HTTP error or when a chunk returns the `QUERY_LIMIT` row cap (to avoid silent truncation — if even the 1-minute window hits the cap, the whole download fails loudly instead of saving partial data). Rows with unparseable timestamps are dropped and counted; if `dropped_count` exceeds `ELASTIC_MAX_DROPPED` the day aborts instead of saving. `should_skip_download`/`plan_download_dates` skip re-downloading a day only if it was already downloaded **and** is fully complete (not "today", not partial) — the current/partial day is always refreshed. These day-planning helpers, like the rest of the engine, are source-agnostic.

### Log storage: ACS (`app/acs/services/log_storage.py`) vs. 3DS (`app/threeds/log_storage.py`)

ACS results are stored as `data/logs/{date}/elastic.log` (+ `elastic.meta.json` with `partial`/`rowCount`/min/max datetime) via `save_elastic_log`. This module **also** still understands the legacy `acs1`/`acs2` upload format (`save_upload`, paired-file validation) purely for backward compatibility with previously-uploaded data on disk — `read_day_for_parse` prefers `elastic.log` for a day when present, falling back to the `acs1`+`acs2` pair otherwise.

3DS Server results are stored separately as `data/logs_3ds/{date}/elastic.log` (+ `elastic.meta.json`) via `app/threeds/log_storage.py`'s own `save_elastic_log`/`read_day_for_parse` — a much smaller module since there's no legacy upload format to support; it adds `read_log_content()` for the desktop Raw Log viewer. Storage dir is overridable via `THREEDS_LOG_STORAGE_DIR` (parallels `LOG_STORAGE_DIR` for ACS).

### Parsing pipelines: `app/acs/parsers/acs_log_parser.py` vs. `app/threeds/parsers/threeds_log_parser.py`

Both parse one calendar day's raw log text into a list of per-message dataclass rows (`MessageRow` / `ThreeDsMessageRow`, in each tool's own `models.py`), via the same `parse_log_content`/`parse_log_files` entry-point shape: lines are matched against `TIMESTAMP_RE` first (skip if no match), then routed by substring/regex match in each tool's own `patterns.py`; JSON payloads are parsed generically (array-or-single-object, tolerant of key order — message type is read from the *parsed* dict, never regex-sniffed from raw text) and mapped onto the row via each tool's own `field_mapping.py`'s `JSON_FIELD_MAP`. Rows get a `source_index` (`file_index * 10_000_000 + line_no`) so multi-file merges sort deterministically by `(message_datetime, MESSAGE_SORT_ORDER[message_type], source_index)` — `MESSAGE_SORT_ORDER` in each `models.py` defines canonical event ordering within the same timestamp. Malformed JSON is never silently swallowed: both parsers take a shared `app.common.parse_diagnostics.ParseDiagnostics` instance and record a drop reason per bad payload; callers compare `diagnostics.dropped_count` against `max_dropped_lines()` (`PARSER_MAX_DROPPED` env var, default 100, shared by both parsers) and refuse to save the day's CSV if exceeded — same "fail loud instead of dropping data quietly" philosophy as the Elastic downloader. (`acs_log_parser.py` re-imports `ParseDiagnostics`/`max_dropped_lines` from `app.common.parse_diagnostics` at its original module path so existing imports keep working.)

**ACS-specific:** message types are `AReq`/`ARes`/`CReq`/`CRes`/`RReq`/`RRes`/`Erro` plus several plain-text-only ones (`ChallengeMethod`/`ChallengeAnswer`/`ChallengeOutcome`/`ChallengeExpiring`/`AuthMethodSwitch`/Oob*) matched by dedicated regexes in `patterns.py` — not present in the JSON-wrapped lines at all. **Known quirk** (see `patterns.py` comment and `tests/test_auth_method_switch_ids.py`): the ACS log swaps the `acsTxnId`/`tdssTxnId` labels specifically in the "Switch auth method" line — `acsTxnId` there actually holds the 3DS Server transaction ID and vice versa. Every other challenge-related line uses the labels normally. `AUTH_METHOD_SWITCH_RE`'s group mapping intentionally differs from the others — don't "fix" it to match.

**3DS-specific:** message types are `AReq`/`ARes`/`CReq`/`CRes`/`RReq`/`RRes`/`PReq`/`PRes`/`Erro`, all JSON-wrapped — no plain-text protocol messages. `PReq`/`PRes` (periodic card-range preload) carry their own unrelated `threeDSServerTransID` that never matches any `AReq`'s — they're parsed and stored for completeness but naturally drop out of the per-transaction report via the `INNER JOIN report_txn` gating (see report engine below), no special-case code needed. Two plain-text lines ARE parsed into synthetic rows because they carry data not available anywhere else: `Received RReq for txn[<id>] with status: [SUCCESS|DENIED|REJECTED] / [<REASON>|null]` (`RECEIVED_RREQ_STATUS_RE` → a synthetic `RReqResult` row with `rreq_result_status`/`rreq_result_reason` — this is the human-readable decode of the just-received RReq's `transStatus`/`transStatusReason`, e.g. reason code `"14"` ↔ `TXN_TIMED_OUT_AT_ACS`) and `slr.ipa.tdss.log.3ds_method_expired: [<id>]` (`METHOD_EXPIRED_RE` → a synthetic `MethodExpired` row — fires for ~every transaction, it's the 3DS Method timer elapsing, **not an error**, just an informational flag in the report).

### CSV storage: `app/acs/services/csv_storage.py` vs. `app/threeds/services/csv_storage.py` (+ `app/acs/parsers/csv_writer.py` / `app/threeds/parsers/csv_writer.py`)

- Parsed rows are written one CSV-per-day (`data/csv/{date}.csv` for ACS, `data/csv_3ds/{date}.csv` for 3DS, both `;`-delimited), plus a `.meta.json` sidecar (row count, min/max datetime, whether the day has full 00:00–24:00 coverage — `fullDay`). `CSV_TO_DB` in each `csv_storage.py` is the canonical camelCase-CSV-column → lowercase-DB-column mapping used everywhere reports run (ACS's is hand-written; 3DS's is generated as `{col: col.lower() for col in CSV_COLUMNS}` since there's no ACS-style irregular casing to preserve).
- Both `csv_writer.py` modules enrich every row at write time: if `browserUserAgent` is set, `app.common.device_detection.parse_browser_device()` derives `browserOS`/`browserModel` (regex device/OS sniffing, with an Android raw-model → marketing-name lookup backed by the bundled `app/data/android_model_aliases.json` — regenerate that file with `scripts/generate_android_model_aliases.py`, a dev-only script, not run at runtime).
- `resolve_csv_paths_for_dates` **hard-fails** if any day in a requested range has no parsed CSV ("Report range has unparsed day(s)...") — a report range is all-or-nothing, unlike the old behavior of silently loading whatever existed. Same in both tools.
- `db/init/*.sql` is a **legacy Postgres schema, not used by any code path** — the app never connects to Postgres; DuckDB reads the CSVs directly.

### Report engines: `app/acs/services/file_report.py` (+ `db/report_query.sql`) vs. `app/threeds/services/file_report.py` (+ `db/report_query_3ds.sql`)

Both are near-identical in mechanics (duplicated rather than shared — see "Why not shared" below) and only differ in table name, column set, and SQL template. CSVs for the requested date range (or all of them) are loaded into an in-memory DuckDB **table** (`cust_acs_3dsmess` for ACS, `cust_3ds_server_mess` for 3DS — a table, not a view, so browser columns can be backfilled via `ALTER TABLE`/`UPDATE` for old CSVs that predate `browserOS`/`browserModel`; see `_enrich_browser_device_columns`, which registers `vst_browser_os`/`vst_browser_model` DuckDB UDFs). `_load_report_result` also calls `app.common.duckdb_time_zone.register_time_zone_functions` (the `vst_st_louis_date` UDF) on every freshly created connection. Either the template query or a user-supplied custom SQL then runs against it.

- `%(date_from)s` / `%(date_to)s` / `%(txn_id)s` psycopg-style placeholders are rewritten to DuckDB `?` params by `_adapt_report_sql_for_duckdb` — the template SQL is authored once and shared between "date mode", "txn ID mode", and as the default loaded into the custom-SQL editor. Both tools' adapter functions rewrite the same `areq`/`ds` table aliases (coincidentally identical naming convention between the two SQL templates).
- Both templates filter their "primary" message type (`AReq`) by the bound params *first* (`report_areq`/`report_txn` CTEs), then every other CTE `INNER JOIN`s against `report_txn` — this keeps the query from scanning the full multi-day table once a narrow date/txn filter is applied.
  - **ACS** (`db/report_query.sql`) computes `general_success` (`YES` if the transaction has any `ARes` with `transstatus` `Y`/`I`/`R+02`, or any `RReq` with `transstatus='Y'` or `transstatus='N'` + `challengecancel` `02`/`05`), a narrative `txn_timeline`, and `txn_result` classified from that timeline (`Erro`/`Timeout`/`OOB_to_OTP`/`Challenge_FAIL`/`Challenge_OK`/`OOB_flow`/`OOB_started`/`Other`).
  - **3DS** (`db/report_query_3ds.sql`) computes `general_success` the same two-CTE way (`success_ares`: `ARes.transstatus='Y'`; `success_rreq`: `RReq.transstatus='Y'` — simpler than ACS's since this message format doesn't have the `'I'`/`'R'+'02'` special cases), a `txn_timeline` over its own message vocabulary (tokens like `RReq(N+14)`, `Result(DENIED/TXN_TIMED_OUT_AT_ACS)` from the synthetic `RReqResult` row, `3DSMethodExpired`), and `txn_result` classified directly from `rreq.transstatus`/`ares.transstatus` into `SUCCESS`/`DENIED`/`REJECTED`/`UNABLE`/`DECLINED_NO_CHALLENGE`/`CHALLENGE_NO_RESULT`/`Erro`/`Other`. Also exposes `rreq_status`/`rreq_result_description` (the decoded human-readable denial reason) and `purchase_amount`/`purchase_currency`/`purchase_date` (available from `AReq`, not present in ACS's report).
  - Both convert `areq.messagedatetime` (assumed to be in `ELASTIC_TIME_ZONE`, default `Europe/Athens` — same UTC offset/DST rule as Ukraine) to the equivalent calendar day in `America/Chicago` via `vst_st_louis_date` — date only, no time, so report rows can be cross-checked against which St. Louis-side day a message landed on.
- A module-level cache (`_materialized_report`/`_cache`, cleared via `clear_report_cache()`) keeps one open DuckDB connection keyed by a CSV-file signature (path+mtime+size) plus the report SQL+params, so paginating through `run_report_query` or re-running with the same CSVs doesn't reload/re-enrich the whole table every call. Each tool's `file_report.py` has its **own** independent cache (module-level global), not shared between tools.
- `export_report_xlsx` writes a `Data` sheet (via DuckDB's `COPY ... FORMAT xlsx` when the `excel` extension loads, else an `openpyxl` write-only fallback), a computed `Summary` sheet (`txn_result` counts + percentages — the 3DS one has no Champions-equivalent sheet, that's ACS-only business logic), and, when `native_pivot=True`, a `Pivot` sheet from `app.common.excel_pivot`: a fully-built native pivot table via Excel COM automation (`pywin32`, only works if Excel is installed and row count ≤ `NATIVE_PIVOT_MAX_ROWS`) or, as a fallback, skipped with an error message surfaced to the UI. Each tool's `file_report.py` defines its own `PIVOT_ROW_FIELDS`/`PIVOT_VALUE_FIELD` matching its own column names and passes them into the shared `add_native_pivot(..., row_fields=..., value_field=...)`.

**Why not shared:** the two report engines' orchestration logic (caching, pagination, SQL adaptation, Excel export) is ~90% identical by line count, but was deliberately duplicated rather than parameterized into one generic module — the two SQL templates, table names, and column sets differ enough that a shared engine would need a config object threading through nearly every function, for a format that's unlikely to gain a third sibling soon. Only the genuinely format-agnostic pieces (device detection, timezone UDF, pivot builder, date/SQL-validation helpers) were extracted to `app/common/`.

### Automation (`app/acs/jobs/daily_report.py`)

A CLI entry point (`python -m app.acs.jobs.daily_report`) that runs the same rolling-window flow as the ACS Log Parser tab unattended: download + parse the last `DEFAULT_WINDOW_DAYS` (10) days via the same `elastic_logs`/`log_storage`/`csv_storage` functions (passing `ACS_SOURCE`), export the report, and email it via `app/acs/services/report_mailer.py` (Outlook COM automation only, through `app/acs/services/outlook_sender.py` — the job silently skips emailing if `REPORT_EMAIL_TO` isn't set, or reports "Outlook automation unavailable" if `pywin32`/Outlook aren't available). Writes a `run-summary-*.json` next to the reports on every run. Not yet wired to a scheduler (no cron/Task Scheduler entry in this repo) — that wiring is external to this codebase. There is no equivalent automation job for the 3DS source yet.

### Config / paths

`app/common/paths.py` resolves the app root/bundle dir (`ROOT_DIR`) and the bundled `db/` dir (`DB_DIR`, holds both SQL templates) relative to the exe/script location (`sys.frozen` check for PyInstaller) — this is the only genuinely shared piece. `app/acs/paths.py` and `app/threeds/paths.py` each build their own storage-dir getters on top of it, overridable via their own env vars (`LOG_STORAGE_DIR`/`CSV_STORAGE_DIR`/`REPORT_OUTPUT_DIR` for ACS, `THREEDS_LOG_STORAGE_DIR`/`THREEDS_CSV_STORAGE_DIR`/`THREEDS_REPORT_OUTPUT_DIR` for 3DS — see Configuration above). `backend/data/`, `backend/build/`, `backend/dist/` are all gitignored — never treat their contents as source.

### Packaging

`vst.spec` lists every `desktop.*`/`app.*` submodule explicitly in `hiddenimports` (PyInstaller can't always discover them via static analysis) — new modules under `desktop/` or `app/` must be added there or they'll be missing from `VST.exe`. Bundled data files: `db/report_query.sql` + `db/report_query_3ds.sql` (loaded via `app/common/paths.py`'s `DB_DIR`) and `app/data/android_model_aliases.json` (loaded via `app/common/paths.py`'s `get_bundle_dir()`). `win32com`/`pythoncom`/`pywintypes` (from `pywin32`, Windows-only per `requirements.txt`) are hidden-imported for the native-pivot COM automation path; the app must still work without Excel installed (`native_pivot_available()` gates it).

## Workflow note (from README)

Dev machine (Cursor) edits/commits `backend/` source; VDI only pulls and runs `build.bat` (or `pull-build.bat`) to rebuild `VST.exe`. `backend/dist/data/` on VDI holds real user data and must never be pushed to git.
